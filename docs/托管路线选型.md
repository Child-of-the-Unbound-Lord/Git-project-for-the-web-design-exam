# 网站托管路线选型

查阅日期：2026 年 11 月 26 日。本文针对 LabFlow 现有网页和本地 Python 版本选路线，尚未创建外部托管项目，也没有完成云端数据库迁移。

## 先用 GitHub 加 Cloudflare Pages

这次先把代码放进 GitHub，再让 Cloudflare Pages 从仓库构建网站。网址用平台分配的 `项目名.pages.dev`，等课程作品稳定下来，再考虑要不要买自己的域名。

这样选，主要是因为现有首页、工作台、指南和下载中心都是 HTML、CSS、JavaScript，迁移时可以继续使用。Pages 支持公开和私有 GitHub 仓库，配置好以后，推送代码就会触发构建和发布，也能为分支生成预览。[1] 两个人协作时，你负责合并主分支，同学先在预览页面检查，确认没问题再发布。

现有项目会生成 `dist` 目录，部署时把它作为发布目录。首页能打开、八个入口能进入、下载文件能取到，是这一轮的验收目标。**网页换了托管平台，并不代表库存已经同步。** 当前浏览器演示版仍把数据保存在各自浏览器里，这一点需要在页面上继续说清楚。

## 下一步再接共享库存

之后保留这些页面，增加 Pages Functions 或 Workers 接口，再用 D1 保存账号、耗材和出入库流水。Cloudflare 的官方文档提供了静态页面与服务端代码一起部署的方式，D1 也有免费试验额度；达到额度后会限制查询或新增数据，不能把“免费”理解成没有上限。[2][3]

这部分新 API **还没有实现**。下一轮先验收一个具体场景：你入库十件，同学在另一台电脑上能看到同一条流水和相同库存。随后检查成员权限、重复提交和库存不足，最后再加备份、恢复。这样每一轮都有能演示的结果，实验报告也能留下真实的改进过程。

如果继续使用 Python 后台，也需要做部署适配。根据本地 `server.py` 的静态审阅，当前服务默认绑定本机地址，Host 校验只接受本机或监听地址，采用本地 HTTP，会话 Cookie 尚未按 HTTPS 部署配置，数据库写入本地 `data/lab.db`。因此不能把它原样上传，就当作已经完成公网部署；域名与反向代理、HTTPS、会话配置和持久存储都要一起处理。

## 其他平台怎样取舍

**GitHub Pages 可以作为备选。** 它只需要 GitHub 这一个平台，能直接托管现有静态网页，并提供 `github.io` 地址。但 GitHub Free 的 Pages 通常需要公开源仓库，而且不能运行服务端 Python。[4] 适合展示作品，之后要共享库存仍需另接后端。

**Render 最需要留意的是数据保存。** 免费服务闲置十五分钟会休眠，本地文件在休眠、重启或重新部署后会丢失，SQLite 数据库也在其中；免费 Postgres 另有三十天到期限制。[5] 因此不把“把现有 SQLite 上传到免费 Render”作为长期方案。

Vercel 和 Firebase Hosting 也能托管网页、提供平台网址，本项目暂时不增加这两套配置，避免两个人同时维护多条部署路线。[6][7]

## 账号、域名和备案不是同一件事

Cloudflare 目前支持 Google、GitHub 社交登录。[8] 这里是开发者登录管理平台；网站访客不需要因此拥有同类账号。今后的管理员、成员登录由项目单独实现，公开首页也不必设置登录门槛。

使用平台默认网址，当前没有购买自有域名这一步。平台账号验证、域名注册实名和服务器接入备案是不同流程；服务商资料也区分中国大陆与大陆以外托管的备案要求。[9] 本项目先按所选平台的正常流程开通，不承诺所有账号都没有验证，也不把某一种托管方式等同于免除任何场景下的全部合规要求。
